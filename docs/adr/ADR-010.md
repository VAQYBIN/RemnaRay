# ADR-010: Remnawave API transport and verified panel contract

- Status: accepted with contract incompatibilities recorded
- Date: 2026-09-19
- Scope: TASK-M0-004 and the future `packages/remnawave-sdk` implementation

## Context

RemnaRay uses a small typed client over `undici` instead of a third-party
Remnawave SDK. The target panel release and the endpoint assumptions in
section 10.1 must be checked before the SDK is implemented.

## Verification

The official Remnawave repository lists `v3.4.4` as its latest release on
2026-09-19. The release publishes the versioned image
`ghcr.io/remnawave/backend:3.4.4`.

The official OpenAPI document was fetched from
[`https://cdn.remna.st/docs/openapi.json`](https://cdn.remna.st/docs/openapi.json)
on 2026-09-19. It reports `info.title = Remnawave API v3.4.4`, OpenAPI 3.0,
162 paths, and SHA-256
`bebc345543b82c66ee1f956333e65cddfb8aec46099bf4427de38fb43df69396`.
The document defines bearer authorization and the documented error envelope
`timestamp`, `path`, `message`, `errorCode`.

No panel credentials were available, so live behavior behind a deployed panel
was not exercised. In particular, the requirement for `X-Forwarded-For` and
`X-Forwarded-Proto` remains a runtime verification item.

## Section 10.1 verification matrix

The checks below compare the requested RemnaRay client contract with the
v3.4.4 OpenAPI document. A failure means the SDK must adapt the current
contract or the supported panel floor must be revised in M2-001.

| Client method              | Result on 2026-09-19     | Finding                                                                                                                                                                                              |
| -------------------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `system.stats`             | ✓                        | `GET /api/system/stats` exists.                                                                                                                                                                      |
| `users.create`             | ✓                        | `POST /api/users` exists; required body fields are `username` and `expireAt`.                                                                                                                        |
| `users.update`             | ✗                        | `PATCH /api/users` exists, but the body uses numeric `id`, not `uuid`.                                                                                                                               |
| `users.getByUuid`          | ✗                        | The route is `GET /api/users/{userId}` and the path parameter is numeric `userId`; no UUID user route is documented.                                                                                 |
| `users.getByTelegramId`    | ✗                        | `/api/users/by-telegram-id/{telegramId}` is absent. `POST /api/users/resolve` accepts `id`, `shortUuid`, or `username`, but not `telegramId`.                                                        |
| `users.getByUsername`      | ✓                        | `GET /api/users/by-username/{username}` exists and returns `UserResponseDto`.                                                                                                                        |
| `users.enable` / `disable` | ✗                        | The action routes exist, but their required path parameter is numeric `userId`, not `uuid`.                                                                                                          |
| `users.resetTraffic`       | ✗                        | The route exists, but its required path parameter is numeric `userId`, not `uuid`.                                                                                                                   |
| `users.revokeSubscription` | ✗                        | The route exists and returns `shortUuid`, but uses numeric `userId` and an optional revoke body.                                                                                                     |

| `squads.list`              | ✗ (corrected 2026-09-20) | `GET /api/internal-squads` returns squads carrying `uuid`, `name` and `info.membersCount`, but wraps them in a page: `{response:{total,internalSquads}}`. Read as a list until a live panel refused. |

## Re-verification on 2026-09-20, against a live panel

The first owner to run the setup wizard against a real Remnawave panel
received `squads.map is not a function` from step 3. The official document was
fetched again from
[`https://cdn.remna.st/docs/openapi.json`](https://cdn.remna.st/docs/openapi.json):
it is byte-for-byte the document of 2026-09-19 — the same SHA-256
`bebc345543b82c66ee1f956333e65cddfb8aec46099bf4427de38fb43df69396`, 162 paths,
`Remnawave API v3.4.4`. Nothing drifted; the row below was read too narrowly
the first time.

`GET /api/internal-squads` answers
`{"response":{"total":N,"internalSquads":[…]}}` — a page, not a list. The
matrix checked that a squad carries `uuid`, `name` and `info.membersCount`,
which it does, and did not check the shape around them. The same is true of
`GET /api/hwid/devices/{userId}`, which answers
`{"response":{"total":N,"devices":[…]}}`, and `DELETE /api/users/{userId}`,
which answers `204` with no body at all where the client parsed one
unconditionally. All three are fixed in `packages/remnawave-sdk`, and
`packages/remnawave-mock` — which had imitated the client's assumption rather
than the panel — now answers with the documented shapes.

The identifier findings of 2026-09-19 are unchanged. The panel's user object
carries `id: number` and **no `uuid` at all**; `PATCH /api/users` takes `id` in
the body; every action route is `/api/users/{userId}/actions/…` with a numeric
parameter; `POST /api/hwid/devices/delete` requires
`{ userId: number, hwid }`; and `/api/users/by-telegram-id/{telegramId}` does
not exist in the document. The documented replacement is
`GET /api/users/stream?telegramId=…`.

The compatibility boundary is now adapted to this contract. The SDK persists
the numeric panel user id for lookups, updates, actions and HWID operations,
uses the documented stream response for Telegram lookup, sends the required
revoke body, and retains `vlessUuid` only as the subscription UUID snapshot.
Migration `0005_panel_user_id` adds the mapping column; old rows without it are
reconciled through the Telegram stream on their next sync. The mock and SDK
fixtures use the same numeric contract. Live acceptance still needs to exercise
a purchase against v3.4.4.

## Decision

Keep the RemnaRay transport boundary as a typed `undici` client and retain
ADR-010 as the compatibility record. The local UUID-based domain identifier
maps to the panel's numeric `userId`; the panel's VLESS UUID remains a
subscription snapshot. Contract fixtures must continue to follow the verified
v3.4.4 OpenAPI document before live panel integration is accepted.
